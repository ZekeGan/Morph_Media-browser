# 決策 2026-11（C-116～C-127）

只增不改的決策全文；索引與「現行／被修訂」狀態在 [DECISIONS](../DECISIONS.md)。


## C-116：移除 CELL 群組與影片專案層播放設定，新專案維持單層（2026-11-01）

使用者核定：
1. **移除 CELL 群組**（S18）：效益小、需決定的規則多。群組型別與驗證已移除，舊專案載入時略過群組及子組件。
2. **新專案預設層級**維持單層第 1 層（自 0.5.0 起；資料測試斷言），取代 2026-10-27「建立預設全部」。
3. **移除影片專案層 `videoAutoplay`／`videoAutoNext`**：影片改走全域播放佇列；舊檔內欄位不再驗證。
4. **資料夾設定一律停靠右側面板**並跟隨目前資料夾；設定開啟時鍵盤／滑鼠上一頁照常導覽，設定隨資料夾切換（有未保存草稿時詢問）。
5. **BOOTH／Melonbooks／虎之穴不接入**；推送先不做。
6. 「遊戲匯入封面圖片按鈕改為前往設定『圖片』分頁」：使用者決定先不做，封面選單維持現狀（含不另加「更多來源」入口）。

## C-117：專案分類退役，行為改由資料夾類型決定（2026-11-03）

使用者核定，相容性不是限制。資料夾類型為遊戲、書籍／漫畫、影音、一般，不確定歸一般，可手動覆寫（`details.kind`）。專案不再有媒體分類與影音轉換；內容模板與版面以類型為鍵（`contentCells`、`kindLayouts`）。匯出版本升為 2，匯入時 `migrateRecord` 把舊分類欄位移除並改鍵。取代 C-47、C-110、C-114 中與專案分類有關的部分。

## C-118：設定、面板與工具列的整理決議（2026-11-03）

使用者逐項核定：右側面板改為「選取即顯示、只由使用者開關」並移除自動開啟偏好；檔案檢視的範圍跟隨路徑列、移除獨立的範圍資料夾；工具列位置固定、檢視切換改純圖示；應用程式設定分「一般／資料與備份」，語言與主題選了就套用；專案的匯入集中在「新增專案」（從資料夾建立／匯入／連結既有專案），匯出與移除在專案設定；說明文字只在偶爾才需要時才收進「？」，狀態資訊留在畫面上；資料夾詳情持有位置（最後兩層）與資料來源連結；舊資料匯入與舊分類鍵別名移除（相容性不是限制）；測試輸出自動清理，打包輸出每版本一個資料夾。規格見 [工作區](../WORKSPACE_REVISION.md)、[UI 規則](../UI_RULES.md)。

## C-119：版本階段、打 tag 與資料自動升級（2026-11-04）

使用者核定：
1. **階段**：Alpha（現在）不打 tag、不公開發布、不保證資料相容；Beta 起打 tag 並以 Pre-release 發布；正式版 1.0.0 起每版皆打 tag。**進入 Beta 只由使用者宣告**，0.40.0 不當 Beta，宣告前一律按 Alpha 處理。
2. **tag 時機**：開發中與 Beta 期間的批次只累積在 CHANGELOG 的 Unreleased，不逐批升版、不打 tag；只有使用者確認「這版可以給人用」才定版、打包、打 tag 並發布；已發布的 tag 不移動，修正就發下一個 `beta.N`。
3. **資料自動升級**（Beta 起必須）：升格式不要求使用者做任何額外操作。`%APPDATA%` 啟動時升級並先備份；資料夾與專案的可攜記錄（含專案私有覆寫）讀取時在記憶體升級，該筆記錄因其他原因存檔時才寫回，瀏覽與掃描不批次改寫使用者收藏，原因是資料可能在離線硬碟或隨身碟上。
4. **較新版本的資料**：舊版程式遇到更高的 `schemaVersion` 時唯讀顯示並提示更新，不當成損壞、不寫入、不清理。

規格見 [RELEASING](../RELEASING.md) 與 [DATA_FORMAT](../DATA_FORMAT.md#格式升級與相容規則)。

## C-120：簡化移除與清理入口（2026-11-04）

使用者核定：
1. 專案設定「資料」分頁只留一個「移除專案」區，單選三級：只取消連結（預設，最保守）、只移除此專案的資料、連同共用資料一併清除；後兩級沿用原預覽、影響其他專案名單與確認流程，取消連結不再是獨立區塊，也不再收在「危險操作」摺疊。
2. 拿掉「清理全部已連結資料」的入口（應用程式設定與編輯器頁底部，後者實際未顯示）及 `cleanupAllPreview` 動作；要徹底清理時，對每個專案各做一次「連同共用資料一併清除」。底層清理程式與 `all` 範圍保留給測試，不再有介面入口。
3. 備份集中在應用程式設定「資料與備份」（設定包與復原點），專案資料匯出留在各專案設定「資料」分頁、匯入留在「新增專案」，應用程式設定內以一句說明指向兩處；取代原先「把匯出集中到資料與備份」的構想，因為匯出需要先選專案。
4. 用詞統一為：取消連結、移除專案資料、清除共用資料。

## C-121：備份只留「備份」與「還原」（2026-11-04）

使用者核定：設定包匯出入、專案設定的「匯出專案資料」、新增專案的「匯入匯出的專案資料」合成應用程式設定裡的兩個按鈕。「建立備份」一次存下設定與所有專案的資訊（不含媒體）；「從備份還原」先預覽，可只勾選部分專案，找不到原資料夾時可選新位置或略過。備份資料夾內沿用既有的設定包與專案匯出格式，加一份清單，不新增記錄格式。取代 [C-120](../DECISIONS.md#c-120簡化移除與清理入口2026-11-04) 第 3 點。已實作，備份位置後由 [C-124](../DECISIONS.md#c-124備份改成程式內的一張清單2026-11-04) 調整。

## C-122：移除專案改成兩個按鈕，共用選項只在需要時出現（2026-11-04）

使用者核定（第二組全做）：專案設定的移除改成「從清單移除」與「刪除這個專案的資訊…」。刪除預設只移除這個專案的設定與私有資訊；勾選預設不勾的「也刪除這些資料夾裡 M:orph 建立的其他資訊」才完全移除，並列出也使用這些資料夾的已連結專案。原提案「沒有其他專案時自動完全移除」經獨立審查後未採用：完全移除也會刪掉從清單移除過的專案定義、舊封存與遊戲判斷，而離線或其他電腦的連結無法偵測。同批：資料夾設定的「共用／僅目前專案」切換只在其他已連結專案也顯示同一資料夾、或這個專案已有私有資訊時出現；疑似遊戲的提示直接提供「確認為遊戲主資料夾／這不是遊戲目錄」；資料夾進階頁的清除不再收在「危險操作」摺疊。取代 [C-120](../DECISIONS.md#c-120簡化移除與清理入口2026-11-04) 第 1 點的三級選擇。

## C-123：新增專案只剩一步，舊專案自動提示接回（2026-11-04）

使用者核定（第二組全做）：新增專案對話框只留「選擇資料夾」。所選資料夾裡已有不在清單上的專案定義時，提示「接回原本的專案」（沿用連結流程，以對話框選擇的權杖連結，不另開對話框），也可改為建立新專案；「匯入匯出的專案資料」改由備份還原處理（[C-121](../DECISIONS.md#c-121備份只留備份與還原2026-11-04)），「連結既有專案」頁籤移除，問題畫面的重新連結開同一個對話框。

## C-124：備份改成程式內的一張清單（2026-11-04）

使用者核定：原本「建立備份」是匯出到使用者選的位置，另有一份只含設定、會自己越長越多的「回到之前的設定」清單，兩者都叫備份但行為不同。改成一張清單：「建立備份」直接存在程式資料夾、不問位置；還原前自動備份一份（標為「還原前自動備份」，只留最新 5 筆）；每筆可還原、匯出到別處、刪除；別處的備份用「從檔案還原…」。舊的設定復原點不再顯示（仍保存在 `workspace-backups`）。代價是備份佔用程式所在磁碟空間，介面提醒把備份匯出到其他磁碟以防硬碟故障。取代 [C-121](../DECISIONS.md#c-121備份只留備份與還原2026-11-04) 的「建立備份時選位置」。

## C-125：還原不再自動建立備份，只為設定提供退路（2026-11-04）

使用者提出疑問後檢討 [C-124](../DECISIONS.md#c-124備份改成程式內的一張清單2026-11-04) 的「還原前自動備份」：還原專案只補缺少的檔案、不覆蓋現有資訊，自動備份也無法把補上的東西移除，等於給了假的退路；會被取代的只有設定，而設定包本來就會在取代前另存一份。因此拿掉自動備份與自動清理，清單只放使用者建立的備份；還原設定後在備份頁顯示「回到還原之前」（使用設定包的那份存檔，保留到下一次還原設定或使用者按「知道了」）。原則：退路要對應實際會被破壞的東西。日後若加入「還原時覆寫現有資訊」的選項，才需要在選了覆寫時先做完整備份。

## C-126：記錄升級只有一套，匯出包只升包裝（2026-11-05）

[DATA_FORMAT](../DATA_FORMAT.md#格式升級與相容規則) 原寫「匯出的 `migrateRecord` 併入同一份註冊表」。實作時發現 `migrateRecord` 升的是匯出包的包裝格式（`EXPORT_VERSION`，例如匯出 v2 的資料夾類型整合），與記錄本身的 `schemaVersion` 是兩件事。做法：匯出包、備份匯入時先由 `migrateRecord` 升包裝，再把每筆記錄交給 `shared/upgrade.ts` 的同一份 `UPGRADE_STEPS`；記錄格式因此只有一套升級鏈，達到原規則「不維持兩套」的目的。另外，較新版本資料在 IPC 間以訊息文字辨識（`isNewerFormat`），視窗端據此不提供恢復與重新連結。

## C-127：主規格只寫現行規則（2026-11-05）

依 WORK_ITEMS 的「規格整理」：遊戲引擎辨識規格改寫成對照 `electron/game-detection.ts` 的現行規則表，移除 2026-10-27 的逐案診斷紀錄、已修正的「現有缺口」表與使用者收藏的作品名稱（舊內容在 git 歷史，提交 `1ac88f3` 之前的版本）；工作區規格的移除與設定包段落改成 C-122／C-125 之後的現況；各規格標題拿掉日期註記（被連結的舊錨點以 `<a id>` 保留）。日期與理由一律記在本頁，規格頁首標示最後確認日期。

## C-128：需求清單、狀態區塊與領域登錄表（2026-11-05）

使用者核定（七點照建議）：需求先登記不實作，補齊大小、風險、資料影響、領域、依賴、取代；核定「建議下一批」即核定該批需求；只在大型或會寫入資料時多回一句預估；每次回覆結尾附狀態區塊（`pnpm status`）；暫定欄位在畫面查收通過時自動轉正，UI 測試也在轉正時才寫；領域、規格、程式、測試的對應只在 `docs/areas.json`，UI 測試挑選、過時檢查（`pnpm stale`）與任務索引表都由它推導；決策紀錄拆成索引＋按月份全文。理由：使用者每次都要口頭問「還剩什麼、怎麼排」，需求結束後受影響的功能與文件常被放著；前端變化大又常牽動資料結構與測試。CLAUDE.md 同批精簡（命令與驗證細節移到 IMPLEMENTATION）。

## C-129：影片格式維持現狀，播不了就用外部播放器（2026-11-05）

使用者決定不擴展影片格式支援（不附帶 FFmpeg 轉封裝／轉碼、不換 mpv）。現況：MP4（H.264／AAC）與 WebM 內建播放；其他格式播放失敗時說明原因並提供「用系統預設播放器開啟」。理由：附帶 FFmpeg 會增加約 80MB、授權需與自訂授權一併確認，並新增外部程式的安全邊界；目前以外部播放器補位即可。需求清單的 R-213 一併移除。

## C-130：不支援 Mac 原生遊戲啟動（2026-11-05）

使用者決定 R-212（Mac 原生遊戲啟動與 plist 主目標）不做：Mac 上能玩的遊戲不明確，要維護可執行清單成本高。辨識與 `.app` bundle 保護照舊（不寫入、不深入），只是不提供在 Mac 啟動遊戲。程式本身能否在 Mac 執行另案討論。
